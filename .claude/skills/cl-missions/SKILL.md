# Mission trees

The base game's `missions` folder is `replace_path`'d, so a tag has exactly the trees written here. Hand-edit nothing under
`missions/kar_*.txt` (generated); the older hand-written `missions/Reconquista.txt` (Iberia) is checked by the same validator.

## How the base game's mission screen works (read from `countrymissionsview.gui` and 228 vanilla files)

- **Grid of five columns.** A series' `slot` (1..5) is its column; a mission's `position` is its row (1 = top). A cell is 104 x 152 px.
- **One series per column** for a realm (a series is offered when its `potential` holds; `generic = no` beats `generic = yes`).
  Two series for one realm in one column overlap, and two missions in one cell overlap. This mod writes `generic = no`, `ai = yes`.
- **Arrows follow `required_missions`:** straight down to the cell below, a branch to a neighbouring column one row down, a "skip tier"
  line through rows in the same column, a "skip slot" line across a column (two columns away at most). Parents lie in a higher row.
- **Done when `trigger` holds; `effect` is the reward.** `provinces_to_highlight` paints the targets on the map (territorial missions
  must have it). Text is the keys `<mission>_title` and `<mission>_desc`; the title box is 90 x 22 px (two short lines: <= 26 characters).
- **Icons** are `mission_*` sprites of `countrymissionsview.gfx`; the expansions' icon files are not used (not every player has them).
  `python3 tools/missionset.py icons` lists them.
- Vanilla series hold 2..8 missions in up to 13 rows; roots sit in the first row; rewards are prestige, monarch power, a country modifier of
  7300 days (20 years) and permanent claims.

## Data format (`tools/data/missions/NN_name.missions`, one `missions/kar_NN_name.txt` per file)

```
[slug]                                   # the series is kar_<slug>
slot = 1
tags = BYZ,ROM                           # who is offered it (landed tags or formables); `not_tags = X` excludes
select = tech nomad_group ; rank 1,2     # OR instead of `tags`: every realm of tags.db that matches (religion, government, rank, tech,
except = KGZ                             # culture, group; all must hold), minus `except`, minus realms whose column is taken
shield = yes
modifier = kar_x | Name | Description | key value, key value   # a modifier the rewards may use

mission = id | Title | Description       # full key kar_<slug>_<id>
row = 1
needs = a, b, other_slug:c               # parents; slug:id points into another series of the same realm
icon = mission_hands_praying
when = owns 144,145 ; area thrace_area ; dev 300 ; cities 20 ; allies 2 ; subjects 1 ; prestige 50 ; stability 2 ; treasury 500 ; tradition 40
       grown_dev 50 ; grown_states 4 ; home_area ; home_region          # relative to the realm, for generic trees (no ids)
show = province 144,145 ; area thrace_area ; home_area        # default: what `when` asks to own
reward = prestige 10 ; adm 50 ; dip 50 ; mil 50 ; stability 1 ; treasury 100 ; modifier kar_x 10 ; claim 144 ; claim_area thrace_area ; core 144
         claim_neighbours ; claim_neighbour_areas ; claim_home_region  # claims around the realm itself (one per mission)
ai = 250                                 # optional ai_weight
```
Continuation lines of `when`, `show` and `reward` start with whitespace; every other key starts at column 0.

## Generic trees (`17_generic_steppe_and_africa.missions`)

Like the base game's generic missions they use conditions relative to the realm (`grown_dev`, `grown_states`, `home_area`, `home_region`) and claims around
the realm (`claim_neighbours` ...), so one tree fits every realm a `select` picks. A select skips realms whose column is already taken by a series
with explicit `tags` (or by a hand-written file), so a tree written later for a particular tag simply takes that tag out of the generic one. Generic
trees sit in columns 4 and 5 and use `shield = no`; keep their text free of proper names. The potential is written out as the resolved tag list.

## Workflow

```bash
python3 tools/missionset.py which TAG        # the grid a realm sees, column by column, and the arrow kinds
python3 tools/missionset.py owned TAG        # what a realm holds at the start (by area, with names)
python3 tools/missionset.py area NAME ...    # an area's provinces, names and owners
python3 tools/missionset.py region NAME      # a region's areas and who holds them
python3 tools/missionset.py new SLUG --slot 2 --tags BYZ --file 10_x.missions   # empty series to fill in (placeholders fail lint)
python3 tools/missionset.py lint             # the data checks; then build + validate
```
Design from CK3's 867 world and the period (CK3 is the only source; do not copy base-game missions). Aim at real targets the realm can reach
in the first generations, keep conquest missions to places that sit in their natural order, and give each realm one to three series.

## Rules the build and validate enforce

Data (`check_data`, `check_flow`): slot 1..5; tags exist; 3..8 missions; rows 1..12, contiguous, one mission per row in a column; first
missions in row 1 and later ones with parents; parents above (strictly lower row); at most two columns apart; no cycles; one series per
column and one mission per cell for each realm; ids unique; icons from the base-game list; title <= 26 characters, description a sentence of
40..320; provinces are land, areas exist; `when` needs a condition and `reward` a reward; rewards inside the budget (prestige <= 30, each monarch
power <= 100, stability 1, treasury <= 300, one modifier of 5..25 years worth <= 1.5 on the idea scale with allowed keys and values, <= 10 claims,
<= 3 claim areas, <= 4 cores); trigger numbers inside sane bounds.

Scripts (`checks/missions.py`, over every file in `missions/`, hand-written included): column, icon, row, trigger and effect present; every mission
has a title and description in localisation (title fits the box); every province, area and modifier exists; every territorial mission marks the
map; each realm gets one series per column and one mission per cell, parents above children, no cycles; **no first mission is already complete
at the start date** (checked against the generated province owners).

No force limit or manpower is ever a reward (troops come from development alone); modifiers use the idea vocabulary, so they cannot carry one.
Unplayed in-game: check `error.log` after the first run (triggers `num_of_subjects`, `army_tradition`, `add_stability_or_adm_power` follow the base game's use).
