# The Karolingians - design notes

The mod is generated by three Python files and nothing else:

| file | what it owns |
| --- | --- |
| `tools/tagdb.py` | the `Tag` database: one object per realm, carrying its land, capital, rank, CK3 title and reasons |
| `tools/build.py` | reads the database and writes `history/provinces`, `history/countries`, `decisions` |
| `tools/validate.py` | checks the result, and fails the build if the mod disagrees with itself |

## What lives here

This file is the *only* home of the mod's prose. The tools contain no comments
and no docstrings: what ships is `tagdb.py` (data plus a terse per-province id
label), `build.py` (the generator) and `validate.py` (the checker), nothing
else. Everything below is the rationale that used to live in the code, moved
out wholesale - why a rule exists, what it replaced, and what was wrong before.

A comment is a liability with a half-life. Two false premises rotted into
shipped game files: a Crete note once claimed CK3 modelled no Crete at all (it
does, as `d_krete`), and that invented an emir whose reign predated his birth.
Prose gets re-read exactly when it is moved somewhere people look again, so
everything lives here, referenced by name, and the code keeps only the
shebang, `noqa`/`type:` pragmas, and the one-line labels that make a bare
province id legible.

A stale comment is not a neutral thing. Prose that ages badly is better in one
reviewable file than scattered through code where nobody re-reads it.

## The build - one command

`python3 tools/build.py` builds the entire mod from the base game, CK3 and the
spec, and exits 0 only if every check passed. Two files are the whole build:
`tagdb.py` holds the data - one `Tag` object per realm, each carrying its areas
and its provinces - and holds nothing else; `build.py` reads that data and
turns it into files: the allocation, the country files, the empire decision and
the CK3 ruler sync.

The side tables exist because the database does not keep everything: the named
land blocks (`BYZ_ALL`, `ARABIA_ALL`, `BUL_ALL`, `MOGYERS_LEVIDIA` and the
rest) live in `tagdb.py`, so a tag's land is not defined in two files at once.
They are computed from the same `provdata.json` cache, by the same `_owned()`
and `_area()` helpers, as they were when they sat inside `build.py`. The two
province-FILE text transforms, and the constants only they use, rewrite a
file's text rather than naming land, so they stay in `build.py` with the writer
that calls them.

**Why the phases are one file.** The work used to be split across phase modules
that had to be run in an order nobody could remember, and two of those orders
silently broke things: running `gen_countries` before `ck3ruler` reverted all
fifteen CK3-sourced rulers to their hand-written pre-lift names, and letting
the province files drift out of step with the country files. In one file the
order below is just the order the statements run in, so neither bug has
anywhere to hide.

**Why the probe runs before the cache is read.** The allocation tables that
follow are derived from `cache/provdata.json` when the file loads, so the
snapshot has to be refreshed above them rather than inside a build step. That
is why the probe looks like a phase that runs before the phases. The whole
cache directory is gitignored, so on a fresh clone it does not exist and
writing `provdata.json` into it would raise `FileNotFoundError`; it is created
where the probe lives so `probe.py` also works when run on its own. The probe
runs a `vanilla_is_newer()` check, and derived directories are defined once so
that a module building one with `os.path.join` (a `str`) and another with `/`
(a `Path`) cannot disagree.

## Reading vanilla's files

- `parse` returns `(initial_scalars, initial_cores, all_cores, hre_any)` from a
  province file: the undated header block, the cores it carries, every core the
  file ever grants, and whether any dated block mentions `hre`.
- `parse_block_file` returns the top-level `key = { ... }` blocks of a Paradox
  file as `(key, [lines])`.
- `load_region_areas` reads `region -> [areas]`; `load_provinces` reads
  `pid -> dict(owner, controller, cores[], culture, religion, hre, capital,
  name)`.
- `_owned(tag, ...)` is province ids owned by `tag` **at the 1444.11.11
  start**, filtered by region. It reads `owner_1444`, not the top-level
  `owner`: the top level of a vanilla province file is the state before any
  dated block fires, and 158 provinces have an owner or core change dated
  inside `(867, 1444]`. Erzincan is the case in point: top level says TIM with
  `add_core = TIM`, but a `1402.1.1` block gives it to the Aq Qoyunlu and
  removes the Timurid core. This mod ships no `defines.lua`, so it runs on
  vanilla's 1444.11.11 start and the resolved value is the true one.
- `_region` is the region of a province id, via its area (None if unknown).
  `_area` is the province ids belonging to any of the named areas, sorted and
  de-duped, used where a transfer was specified as "these areas" rather than as
  a list of 17 bare numbers - the code says what was asked for. Membership
  comes from `provdata`'s `areas` index, the same source `_owned()` reads
  owners from, so an area and the provinces in it can never disagree.
- `split_header_and_blocks` yields `(date_or_None, block_text)` for the header
  and each dated block; `effective` replays them to `START_DT` and returns the
  owner/controller/cores as of that date. It is the same dated-history replay
  `check_start.py` uses, so the two tools cannot disagree about a start.

### check_start replays the files, it does not re-derive the plan

`check_start.py`'s job is to replay the *written* province files up to the
start date and check the result. The allocation is not re-derived there - it
comes from `build.build()`, the single specification of who owns what. An
earlier version read `cache/alloc.json` directly, which checked none of the
eastern transfers because those live in the generator, and a still earlier one
kept its own copy of the tag list, which drifted. Provinces whose *undated*
header declares no owner at all are only acceptable for the deliberately
unowned Balaton parking provinces; everywhere else the province is populated by
a dated block, so the replay falls back to eff. The check reads `effective()`,
which is exactly what `check_start.py` reads, so a start can never be argued
two ways.

Vanilla's 367 Azores and 368 Madeira are exactly the header-ownerless case:
uninhabited in the header, settled by a `1427.11.29` block that gives them to
POR, and only in scope now because the ADU transfer takes Portugal's islands. A
deliberately unowned province (the Balaton parking lot) has neither owner nor
controller, which is consistent; only a half-set pair - one present, one not -
is a defect.

### Line endings

CK3 ships some files with CRLF and some with LF, and the character files are
mixed. The brace-walkers match `key = {` at the start of a line, so a stray
`\r` must not break block boundaries - every reader normalises line endings
first. The key charset includes `-` and `.` as well as word characters:
`names/character_names_l_english.yml` has entries like ` Al-Mu_tazz:1
"al-Mu'tazz"` alongside plain `Abbasid:0 "Abbasid"`, and a `\w`-only key class
silently drops every hyphenated key - which is exactly why al-Mu'tazz's name
once came out as the raw untranslated key "Al-Mu_tazz".

`_inner_blocks` yields `(key, body)` for nested blocks. Its leading
`[       ]*` is load-bearing: every nested block inside a title is indented
with a tab, so anchoring at `^` with no indent allowance matches nothing at all
and silently yields zero blocks.

## How a realm's 867 ruler is found

Each realm's 867 name and dynasty come from CK3, read at run time from the
game's own files. Two things are stated on the `Tag`, once, in `tagdb.py`:

- `ck3_title` - the CK3 title whose 867 holder supplies the ruler.
- `no_ck3` - why this realm is *not* CK3-sourced, where it is deliberately its own.

A realm in neither list is reported as unclassified and fails the build, so one
cannot be added and forgotten.

**Titles, not character ids.** An earlier design keyed the registry on CK3
character ids, on the argument that ids are exact file facts while titles get
reassigned and vacated between bookmarks. That argument was right and the
design was still wrong: storing a character id is a second, hand-entered fact
that can disagree with the title it is cross-checked against, and nothing
notices. Reading the holder of a title at run time leaves only one fact in the
file, which is the only fact in it.

`ADU` is the case that settled it. It read `c_granada`, a county, and took its
ruler from the county's holder - so a realm holding all of al-Andalus, seated at
Cordoba, was ruled by the sheikh of a town inside it and named for that town. The
title it wanted all along was `k_andalusia`, which is what it reads now.

**Cross-checking is advisory.** Where a tag names a title, the build confirms the
holder really is that title's 867 holder. Where the two deliberately disagree -
`ADU` again - the character wins and the check is skipped, because the mod's
867-flavoured reading is the point.

**Crete.** CK3 does model Crete, as `d_krete`, spelled the Greek way. An earlier
search for "crete" found nothing, concluded the island was absent, and exempted
`CRT` from the audit. The file it then hand-wrote named Abu Hafs Umar, born 838,
as Emir of Crete from 824 until 875 - his father's reign, given to him, and a
reign that could not have begun before he was born. CK3's `d_krete` is held in
867 by **Shuayb**, Abu Hafs' father, who held the island until his own son took
it in 870. `CRT` is now checked against CK3 like any other realm, and `deferred`
remains its status - there is a title to audit, so CK3 can supply the name.

**A vacant own title.** A realm is read from its *own* CK3 title, but where that
title is vacant in 867 the ruler comes from the title declared in
`RULER_TITLES`: SAR's `d_sardinia` is empty 843-1164, so `c_arborea` rules it.

**The CK3 ruler reading per realm.** These are the reading notes that used to be
spliced into the shipped country files. They are the source of the verbatim
lift: `build.py --fix` rewrites each generated realm's ruler name and dynasty
from CK3, and validate fails if the file and CK3 disagree. Do not hand-edit
name or dynasty.

- **FRA** - `k_france`'s holder at 867.1.1 is character 90104, "Charles", of
  dynasty 25061 "Karling". CK3 gives him no epithet; "Charles the Bald" is the
  mod's display name.
- **LOT** - `k_lotharingia`'s holder at 867.1.1 is character 144998, "Lothaire",
  of dynasty 25061 "Karling". CK3 writes that name **unquoted**, with no epithet.
- **GER** - `k_east_francia`'s holder at 867.1.1 is character 90107, "Ludwig",
  of dynasty 25061 "Karling". No epithet; "Louis the German" is the mod's.
- **BAV** - read from `d_bavaria`, not `k_bavaria`, on purpose: CK3 has no
  independent Bavaria in 867. Its `k_bavaria` is held by Ludwig (90107) - the
  same man as `k_east_francia` - continuously from 826.1.1 until 876.1.1, and
  Carloman only takes it in 876. Since this mod splits Bavaria off as its own
  realm, `d_bavaria` is the title whose 867 holder is Carloman (42018, dynasty
  25061 "Karling"). Mapping to `k_bavaria` would have made this a second
  "Ludwig"/"Karling" and erased the realm.
- **ITA** - `k_italy`'s holder at 867.1.1 is character 30228, "Louis", of dynasty
  25061 "Karling". No regnal number; "Louis II" is the mod's.
- **SOR** - CK3 models no Sorbian title at all: `k_sorbs` and `d_sorbs` both have
  no holder, so `d_lausitz` is the nearest title with an actual 867 ruler -
  character 184007, "Radomil", of the Milczanow dynasty. That replaced the
  hand-written "Mstivoj"/"of Lusatia"; Mstivoj survives as the heir below.
- **SIL** - `d_lower_silesia`'s holder at 867.1.1 is character 82293, "Gardomir",
  of the dynasty CK3 spells "Slezan" with diacritics. The hand-written "Gardomir
  Slezan"/"Slezan" was already a guess at exactly this, so only the spelling is
  new.
- **GMA** - `k_moravia`'s holder at 867.1.1 is character 187002, "Rostislav", of
  the Mojmird dynasty. The hand-written "of Rostislav" was invented; CK3 calls
  the house Mojmird.

**Names are read three ways because CK3 writes them three ways**, and all three
occur in the files this mod reads:

```
name = "Nayih"                   quoted
name = Lothaire                  bare, unquoted - 698 such lines in CK3's
                                 characters, including Lothair II, who holds
                                 k_lotharingia
name = "Muhammad" # Muhammad (I)  quoted with a trailing comment, the most
                                 common form of all
```

Anchoring to end-of-line would drop the commented form, so the reader matches
the value and stops at the comment instead. CK3 character names are
localisation keys when they need one ("Al-Mu_tazz" is defined as "al-Mu'tazz"),
and the localisation is preferred so the apostrophe comes out right. The
localisation index scans the whole English tree once and indexes by key rather
than re-walking ~1250 files on every call - the earlier per-key version looked
correct but cached every match it saw while scanning for one key, so the first
lookup populated the cache with a single entry and every later lookup
short-circuited on "cache is non-empty" and returned None for perfectly valid
keys. CRLF is tolerated explicitly, because CK3's yml files carry `\r\n` and
these lines sit at end-of-file positions where a strict `$` anchor after the
closing quote silently fails to match. First definition wins, so a later file
cannot shadow an earlier one for a key that is genuinely defined twice.

**Dynasty houses, and the Abbasid bug.** A character usually names a
`dynasty = <id>`; some name only a `dynasty_house = <house>`, and then the
house is the authority. For the house case the house's OWN name key wins, not
the dynasty the house nests: `house_cantabria` declares `dynasty = erwigiana`,
but its own name key is `dynn_Cantabria`, and "Cantabria" is what identifies
the house the character actually sits in - the reason ASU is "Cantabria" and
not "Erwigiana". The nested dynasty is only a fallback for a house that
declares no name at all. The house parser deliberately accepts an unquoted
value, because `house_abbasid` is the one house in CK3's file that writes
`name = dynn_Abbasid` with no quotes, and a quoted-only pattern would read that
house as having no name at all.

That tolerance is hiding a CK3 bug the mod works around, not a mod choice.
`common/dynasty_houses/00_dynasty_houses.txt` declares

```
house_abbasid = { name = dynn_Abbasid  dynasty = 7296 }
```

but 7296 is declared in `common/dynasties` as `dynn_Hashimid`. So the Abbasid
house points at the Hashimid dynasty, and copying the nested dynasty would give
al-Mu'tazz - an Abbasid caliph in CK3's own history - a Hashimid dynasty name.
The house's own name key is correct and is what the mod uses.

**Continuity versus abandonment.** CK3 does not write a holder into every
title's 867 block. `k_egypt`'s holder is set at 866.1.1; `k_france`, `k_italy`,
`k_lotharingia` and `k_east_francia` carry their holders forward from
840/843/855/866 with nothing dated 867 at all. That is normal - the state is
real, it is simply recorded by continuity - so the holder is still returned.
But the caller is told which block it came from, because a naive "last block
wins" cannot tell continuity apart from a title that simply stopped being
updated, and mistaking one for the other would report a confident wrong name.

The `resolve()` map holds one fact per realm - `which title` it corresponds to -
and is built by looking the title's 867 holder up at run time, so it cannot
come to disagree with itself.

## How a realm's country file gets written

`Tag.country` is the whole instruction. build.py holds no list of realms, so a
new realm is one entry in `tagdb.py` and no edit at all in `build.py`. Five
modes:

| mode | build does | realms |
| --- | --- | --- |
| `fresh` | writes the file from scratch: capital, culture, rank, ruler | LOT, GER, BAV, ITA, SOR |
| `vanilla` | copies vanilla's, then patches capital, rank, the 1444 ruler, and the vote if it has one | FRA, NAV, CRT, SIL, GMA, MON, PRU, BOH, SAR |
| `elector` | copies vanilla's, changes one line - the 1444 vote | BRA, KOL, MAI, PAL, SAX, TRI |
| `written` | nothing; the repo owns the file and build must not touch it | ASU, ADU, ARB, EGY, DAL, BYZ, BUL, HUN |
| `none` | nothing; there is no file | CRI (deferred), POL, PAP |

A realm in `vanilla` mode keeps its whole later history and replaces only the
start this scenario asks for - `patch_vanilla` changes only a capital, the
government rank, the 1444 ruler and whether the country is an imperial elector,
and preserves everything else verbatim, so a vanilla tag keeps Zizka and the
defenestration of Prague for Bohemia and the Piast line for Silesia, and only
its 867 start is replaced. The seven electors all get their vote dissolved,
which is why `BOH` is in two modes at once: a realm the mod patches *and* an
elector stripped of its vote.

The seats and rulers, where the choice was a decision rather than a copy:

- **SIL is seated at 264 Breslau**, the seat of the Silesian duchy - Ratibor was
  an appanage seat - and a province inside what SIL holds.
- **PRU is seated at 1841 Marienburg**, inside `east_prussia_area`. The
  Pruthenians of 867 held this coast without towns, so the seat is a choice of
  province rather than a settlement of the date.
- **NAV is seated at Pamplona and MON at Zeta**, the seats those two realms
  actually used; the land the mod gives them lies around those seats, not under
  a new one.
- **FRA's ruler block is hand-written rather than read from CK3's dates.** CK3
  dates Charles the Bald 823.1.14 - 877.6.10, a placeholder next to the
  13 August 823 and 6 October 877 every chronicle gives. `ck3_sync` still lifts
  his name and dynasty from CK3; only the dates are the mod's.

### Patching rules that must be literal

- A **patched capital line is a plain line**. The vanilla comment on that line
  names the old seat, so it goes with the old number; a patched line gets no
  trailing comment naming the number it replaced.
- `government_rank` is matched **top-level only, at column 0**. The same key
  indented inside a dated block is a later state of that key, and `count=1`
  would rewrite whichever came first in the file. Vanilla France has
  `government_rank` inside its 1792 revolution block, so a pattern that allowed
  leading whitespace silently rewrote the Revolution's rank instead of setting
  the kingdom's.
- **Eight of the twenty realms have no `government_rank` in vanilla at all**, so
  they silently fall to EU4's default of 1. That is how the Tulunids ended up
  ranked level with Silesia: not a decision, an omission. Every one of them is
  set from `RANK` so the tier is always deliberate. Where there is no line to
  patch, one is added beside the other government keys so the header stays
  readable rather than gaining a stray line at the end; where there is, the
  replacement is inserted before the first dated block at or after the start
  date so chronological order holds.
- `step_countries` builds the text **before writing it**: `open("w")` truncates
  before its argument is evaluated, so writing `patch_vanilla(...)` inline left
  a 0-byte file whenever an assert fired - and 0 bytes look clean to every grep
  check. Build first, write second.

### Disbanding the Holy Roman Empire

There is no empire switch to flip. A country is an elector purely because its
own history says `elector = yes` - `common/empire/electors.txt` ships empty,
and `DESIRED_NUM_OF_ELECTORS` in defines.lua only sizes how many the emperor
would LIKE, not who is one. Dissolving the empire therefore means dissolving
its electorate.

Vanilla does exactly this, and says so in its own comments. Seven country
files carry `1806.7.12 = { elector = no }` - the Reichsdeputationshauptschluss,
the real abolition of the HRE - and REG's reads `1806.7.12 = { elector = no } #
the HRE is dissolved`. That dated block is why a 1821 start date has no Holy
Roman Empire: the history is read up to 1821, every elector has been set to
`no`, and there is nobody left to elect an emperor. A 1444 start simply never
reaches those dates.

So to get that same end state at 1444 we write the dissolution ourselves, one
state at a time instead of one dated block per country: the top-level
`elector = yes` of each 1444 electorate member becomes `elector = no`, which is
vanilla's own syntax for the empire's end. No on_action, no defines override.

Only **seven** files get this, because only seven have a TOP-LEVEL
`elector = yes`. That qualifier matters: Regensburg and Hessen also have
`elector = yes`, but only inside dated blocks from 1803, when the
Reichsdeputationshauptschluss gave them electoral dignity. At 1444 they hold no
vote at all, so they need no override and their 1803-1806 history is left
untouched. The regex is anchored `^` with no leading-whitespace class on
purpose: only a top-level `elector = yes` is a vote in 1444, and matching
`\s*` would silently rewrite 1803-1806 history. validate.py's `electors_as_of`
applies the same rule in reverse - a column-0 `elector = yes` is the baseline
state, the same key inside a dated block is a later state that counts only once
that date has arrived, and grepping for the key at all would demand an override
for Regensburg, which only gains a vote in 1803 and holds none in 1444.

Bohemia matters twice over: it is one of the seven electorates, and it is also
the one this mod patches for its own ends, so its vote goes with the patch.

## What the 867 ruler sync does - and does not touch

The last thing this script did to a ruler used to be to type its name and
dynasty in by hand, which meant the generator and `ck3ruler.py` each held their
own copy of the same fact - and running this script silently reverted all
fifteen CK3-sourced rulers to the pre-lift strings ("Charles the Bald", "of
Rostislav", Mstivoj/"of Lusatia"). So the generator no longer decides those two
fields. It writes the ruler's stats, dates and heir exactly as before, then
asks `resolve()` what CK3's 867 holder's name and dynasty are. One source of
truth, and regenerating is idempotent instead of destructive.

Only name and dynasty are taken from CK3. Stats and dates stay hand-written
because they are judgement calls: CK3's 1-25 skill scale is not EU4's 1-6, and
CK3 has no 1444 to be alive in. Where a ruler is CK3-derived, one conversion is
applied, uniformly: `EU4 = CK3 / 3`, clamped to 1-6. CK3 records no skills at
all for some characters (Miroslav of Duklja is one), and those get a neutral
2/2/2 rather than an invented reputation.

`ruler_for` decides which is which: a hand-written block on the Tag wins over
CK3; anything else with a CK3 title reads 867 from it, honouring `ruler_title`
inside `resolve()` when the realm's own title is vacant in 867.

SIL, GMA and BOH have hand-written ruler blocks, because each needed a
judgement CK3 cannot make for us: which son was the heir, and why a regency is
an artefact of the age shift rather than a fact about 867. NAV and MON need no
such judgement, so their blocks are derived from CK3 instead of transcribed - a
transcription is a snapshot of CK3 that silently rots; this is CK3's own entry
read at build time, the authority the hand-written blocks cite anyway.

**The heir.** The rewrite happens inside the whole 1444.1.1 block, not the
monarch sub-block, so the heir's dynasty is brought along with the ruler's.
Only the ruler's NAME is taken from CK3: the heir is a different man whom CK3
does not model here, so his name, stats and dates are left exactly as the mod
wrote them. The heir is the eldest son CK3 records; CK3 has no gender key on
these characters, so a child is used only where the name is not a daughter's.
Where CK3 records no children at all (Miroslav), no heir is written and the
game generates one - an honest gap rather than an invented son.

**A missing dynasty is not a failure.** Nicholas I, the Pope, is the one mapped
character with no dynasty and no dynasty_house at all - historically ordinary,
since the papacy is not a hereditary house in CK3's model. `resolve_dynasty`
returns None for him, and the mod's own string is left alone instead of being
blanked or invented. validate.py distinguishes the two situations that used to
fail together: a file that DOES carry a dynasty for a character CK3 gives none
is a fabrication and stays fatal (MON and PAP historically declined to invent
one, and the file agreeing with CK3 is the correct, non-fatal outcome).

**A shared dynasty is the point of a divided empire.** All five Carolingian
realms - heirs included - are deliberately one dynasty, because a shared
dynasty is what unlocks Claim Cushion in EU4: claiming a neighbour's throne
without a war. Keeping it unbroken is how the five can put the empire back
together by marriage instead of conquest. It has to cover the heirs as well as
the monarchs, or the dynasty breaks the first time one of these realms
succeeds - which is exactly what Arnulf and Berengar used to do, ending up "of
Carinthia" and "of Italy" on a hand-written dynasty line that quietly diverged
from the house. validate.py fails any realm whose file carries a hand-written
dynasty that silently diverges from the house.

## How land is allocated

Layers 1 and 2 of the allocation live on the Tag for each realm, because the
reasoning is per-realm: "Trieste is Italy's but Krain is Bavaria's" is not a
statement about a province, it is a statement about Italy and about Bavaria.
tagdb.py holds the areas a realm takes whole and the individual provinces it
carves back out of them; this file walks them.

One province is deliberately still declared here. Venice is not a Tag - the mod
maintains no realm for it and takes no land away from it beyond leaving it be -
so its namesake province is the one land-holder this mod tracks without owning,
declared in `UNTRACKED_OWNERS`, where the allocator reads it.

`build()` is `{tag: [province ids]}` - the whole allocation, the one answer.
Areas, then loose provinces, then transfers, in that order and only in that
direction, filtered to the tags the mod actually hands provinces to so a tag
that only appears in a comment cannot leak into the result.

- **Layer 1: areas.** The mod's `areas` declaration, projected straight in.
- **Layer 2: loose provinces**, applied after every area, so one always beats
  its area regardless of the order the dict is written in.
- **Layer 3: transfers.** `claimed` deliberately includes the tag's own
  provinces: the point is to add unclaimed land, never to move land a tag
  already holds, which is what lets the layers compose with no precedence
  table. A later entry wins any overlap with an earlier one - which is why
  Albania sits after Anatolia and why `BYZ_GREECE` is last of all. The order
  and the province lists both come from the database - `Tag.grants` and
  `Tag.grant_order`, where a realm declares what blocks it takes and in what
  precedence.

`ARABIA_MAMLUK` is the Mamluks' land OUTSIDE Egypt, and the only part of
vanilla MAM the Abbasids take: Palestine, Transjordan and the Hejaz coast.
`horn_of_africa_region` is excluded because Suakin (1232) and Halaib (2324) are
Red Sea / Beja land which the Mamluks ruled as Sudan, and Egypt kept those two
when the Mamluks were folded into the EGY tag (see `EGY_ALL`, which exists
because vanilla EGY owns nothing at all, so `_owned("EGY")` would return an
empty list). `THE_OTTOMANS` - the rest of the Ottomans, neither cored nor
Anatolian - is ten provinces, all Balkan: Tarnovo, Silistria, Nis, Vidin,
Plovdiv, Skopje, Kostendil, Tirnovo, Tolcu, Ohrid. Vlore used to be there and
moved to Byzantium with the rest of Albania.

### The allocation, province by province

By area claim, the reasoning sits on each Tag in `tagdb.py`. Reproduced here as
prose - the areas a realm takes whole, the provinces it carves back out, and
the CK3 evidence for each carve-out.

**West Francia.** Septimania (Toulouse, Languedoc, Carcassonne) and Aquitaine -
but NOT Provence/Dauphine (still Lotharingian) and NOT Brittany. West Burgundy
is West Frankish: everything west of the Saone. CK3 agrees on the one county it
places - `c_nevers` under `k_france :: ##d_burgundy` - and Charolais and
Auxerrois have no CK3 867 entry at all, so they follow their area west of the
river. Dijon is NOT taken by the area, because it sits east of the Saone with
the rest of `bourgogne_area`; it is taken as a per-province override below.

Catalonia minus Tarragona. The Catalan counties were Frankish: they sit inside
the Spanish March and Belesarius - sent by Charles the Bald - held Barcelona
and Girona as marcher counts. `catalonia_area` is NOT claimed as a whole
because Tarragona (2988) stays with Aragon, so the four carve-outs below are
claimed one by one instead. Aragon keeps the rest of its 867 holdings.

Flanders is West Frankish in CK3 867: `k_france.txt :: ##d_flanders` holds
`c_brugge`, `c_yperen`, `c_ypres`, `c_guines`, `c_lille`, `c_boulogne` and the
barony CALAIS. It is one of Lothair II's two shortest frontiers and never his -
Louis the German held it as a buffer against the Franks.

Dijon (Dijonnais) goes to West Francia, breaking `bourgogne_area` open. The
Saone was the 867 line between West and Upper Burgundy, and the area split
follows it: Nevers, Charolais and Auxerrois west of the river are already FRA
via `west_burgundy_area`, while Franche-Comte and Salins east of it stay
Lotharingian. An earlier pass took that geography as final and left Dijon with
the rest of its area, which made it the single province where the mod parted
from CK3. It no longer does: `k_france.txt :: ##d_burgundy` holds `c_dijon` in
867, and its holder is Raoul (CK3 character 303420, dynasty 743, Robertine) - a
West Frankish count under Charles the Bald, not a Lotharingian one. Nothing
else in `bourgogne_area` moves.

**Lotharingia.** Lotharingia proper (Low Countries, Moselle, Rhine) plus Upper
Burgundy and the Kingdom of Provence/Arles, all held until 875. Koln and Berg
are Lotharingian, not East Frankish - CK3 puts both counties in `k_lotharingia`
proper (`c_cologne` and `c_berg` sit alongside `c_aachen` and `c_julich` in
`d_rhine`), and the 867 partition left the lower Rhine with Lothair II. Koln
was also never Louis the German's seat, so East Francia's capital moves to
Frankfurt (1876).

The two directions CK3 corrects, to and from West Francia:

- Out of West Francia, to Lotharingia: **the County of Verdun**. CK3 files `187
  Barrois (c_bar)` and `4766 Verdun (c_verdun)` under `d_bar -> k_france`, but
  that is an anachronism: in 867 Bar and Verdun were Lotharingian, held by
  Lothair I and then Lothair II, and only became securely West Frankish after
  Lothair II's death in 869. So `lorraine_area` goes whole to LOT, joining Metz
  and Lothringen (`c_metz`/`c_nancy` under `d_upper_lorraine, k_lotharingia`).
  The Ardennes follow suit: EU4's only land province there is 94 Luxemburg, in
  `wallonia_area`, and CK3 places `c_luxembourg` under `d_luxembourg` in
  `k_lotharingia`.
- Out of France, to Lotharingia - the vice versa half: **1743 Cambray**
  (`c_cambray -> d_brabant -> k_lotharingia`). CK3 puts Cambrai in `d_brabant`
  with Hainaut and Antwerpen, so it is Lothair II's even though it sits inside
  the Picardy area next to France.

**East Francia.** Saxony, Thuringia, Hesse, the Rhineland, East Franconia and
Alemannia (Swabia + the Alemannic Swiss plateau), which Louis was seizing from
857 onward and held outright by the 870s. Transjurania is NOT taken East - CK3
lumps it into `k_burgundy`, but the 867 start sits inside the Burgundian
succession crisis (Rudolf II deposed by Charles the Bald and Louis the German;
the Treaty of Meerssen is two years away), so the mod leaves the 867
county-level reading alone: Bern, Fribourg, Valais and Freiburg stay with
`romandie_area` in Lotharingia, and Geneva goes further still, to Italy.
`switzerland_area` (Zurich, Schwyz, St Gallen, Chur, Illanz) is East, which CK3
confirms in `##d_currezia -> k_east_francia`.

Three deliberate non-moves:

- **1867 Freiburg** stays West Lotharingian even though CK3 files it
  `k_east_francia :: ##d_alsace - so East Francian`, because Bern/Fribourg/
  Wallis have no decisive 867 precedent and stay with the area. Say the word
  and it goes East.
- **203 Lyonnais and 204 Dauphine** stay Lotharingian though they are FRA-cored
  in vanilla. An earlier pass gave them to France for that reason, but CK3 puts
  `c_lyon` squarely in `k_burgundy :: ##d_dauphine` alongside `c_vienne` and
  the rest of the Dauphine, so both belong to the Kingdom of Burgundy and
  therefore to Lotharingia. They keep their vanilla FRA cores, so France can
  still reconquer them. Within `savoy_dauphine_area` only Savoie (205) leaves
  for Italy.
- `lower_rhineland_area` also holds Trier and Koblenz. The Moselle was East
  Frankish under Louis the German while Aachen (Lothair II's capital) and
  Julich stayed Lotharingian, so the area is split rather than left whole.

Leipzig leaves Lusatia for East Francia. `south_saxony_area` is otherwise
Sorbian, and CK3 backs that: `b_wittenberg`, `b_dresden`, `b_gorlitz`,
`b_bautzen`, `b_meissen`, `b_plauen` and `b_gera` all sit under `k_sorbia` (the
kingdoms holding `d_lausitz` and `d_meissen`), the direct analogue of Lusatia
here. Leipzig is the exception - `b_leipzig` belongs to `c_mersenburg`, filed
under `d_anhalt` inside `k_east_francia` alongside Halle and Magdeburg. So the
area splits: Merseburg's hinterland is East Frankish, the Meissen/Lausitz block
is Sorbian.

**Bavaria.** Bavaria proper, the Nordgau/Regensburg, the Austrian march, Tyrol,
Carinthia and the Carantanian march - NOT Swabia or Franconia (East Frankish).
Bayreuth (Nordgau) is Bavarian but shares EU4's `upper_franconia_area` with
clearly East Franconian provinces (Bamberg, Nuremberg, Coburg), hence the
split. East Swabia is not one realm in 867; CK3 splits it, and so does this
mod:

```
k_east_francia.txt :: ##d_swabia     c_ulm, c_grunningen, c_wurttemberg,
                                     c_baden, c_zollern, c_hohenberg
k_bavaria.txt      :: ##d_augsburg   c_augsburg, c_kempten (barony Memmingen),
                                     c_ravensburg, c_burgau, c_alpsee
```

So Augsburg is Bavarian and stays GER only where CK3 says East Francia, and
Bregenz (barony of `c_ravensburg`, `d_augsburg`) is Bavarian too - already BAV
via `tirol_area`, which agrees with `d_tyrol` also sitting under `k_bavaria`.
`carinthia_area` is EU4's Slovenian area, not Carinthia: it holds Carniola
proper (Krain, Cilli) plus the Aquileian coast (Istria, Gorz, Trieste). The
area goes to Italy, but Carniola is carved back out and stays Bavarian, since
the Heptarchy was Frankish and Lotharingian, never Italian, in 867.

**Italy - north only, Pavia.** Provence and the Istrian coast, both pulled off
their previous holders. `provence_area` was Lotharingian under Lothair II, but
the Kingdom of Italy under Louis II reached to the Mediterranean here, and
Provence is culturally and geographically Mediterranean. From `carinthia_area`
Italy takes Istria, Gorz and Trieste - the old Patriarchate of Aquileia coast -
but NOT Krain and Cilli, which stay Bavarian.

Geneva and Savoie go to Italy, breaking both of their areas out. Neither is a
Neustrian or Lotharingian province at all - CK3 files `c_geneva` and `c_savoie`
under `k_burgundy :: ##d_savoie`, the Alpine kingdom straddling the Pennine and
Graubunden passes - and the mod gives the Alpine west to Italy, which by 867
already reaches the Ligurian and Provencal coast. Geneva leaves `romandie_area`
(Bern, Fribourg and Wallis stay Lotharingian); Savoie leaves
`savoy_dauphine_area` (Lyonnais, Dauphine and Annecy stay Lotharingian). This
supersedes the earlier Transjurania reading, which sent Geneva to East Francia
at the Meerssen line. Nice (a county of Provence until 1388) now follows its
area into Italy and lands in `liguria_area` with Genoa and Albenga. Trent, on
the other hand, is carved out of `tirol_area`: the Bishopric of Trent was
Italian-facing and linked to the Lombard kingdom, while Tirol proper stays
Bavarian.

Central Italy: in 867 there is no Papal State to speak of, so the Patrimony
(Umbria, Spoleto, Terracina) goes to the Lombard Kingdom of Italy under Louis
II rather than sitting with the Pope; Urbino was part of that Patrimony long
before the Montefeltro donations made it a papal fief, so it goes over too.
Rome and the Abruzzi are carved back out and stay as they are. Corsica still
rode with the Lombard duchy of Tuscany in 867, a century before Pisa and Genoa
started wrangling over it, so it follows Italy rather than staying with Genoa.

**Lusatia** is the one part of the map with no 867 claimant in this partition:
the Sorbs were tributary to whoever held the neighbouring marches and are given
their own land here. CK3 has no Sorbian kingdom at all, so this is a mod
decision rather than a reading of `k_*.txt` - it takes the three vanilla-BOH
provinces (SOR-cored and already Sorbian in culture) off Bohemia: the whole of
`south_saxony_area` (the area Wittenberg sits in, and only that - Northern and
Lower Saxony both stay East Frankish) plus Vogtland, carved out of
`thuringia_area` because Plauen and Zwickau were the two halves of the
Sudeten/Voigtland march that kept one foot in each sphere.

**Navarra/Aragon.** Vizcaya and Huesca (Osca) to Navarra: Biscay was a Basque
county under Navarre's sphere, and Huesca came with the Sobrarbe/Appalachian
march that straddled the Pyrenees. Both are carved one at a time because
neither area changes hands as a whole - Navarra's own province (210) and Rioja
(2989) stay put, and Aragon keeps the rest of `aragon_area`. NAV is a vanilla
tag, so it needs no country file from this mod.

**Silesia / Great Moravia.** `silesia_area` changes hands entirely but splits
down the middle: Breslau/Liegnitz/Glogau west to Silesia, Opole/Ratibor east to
Great Moravia. File names and in-game names diverge here - the player sees
Wroclaw, Legnica and Glogow, and the game stores those as "Breslau",
"Liegnitz" and "Glogau". Great Moravia takes the whole of `moravia_area` (Brno,
Olomouc, Ostrava), giving it a real Moravian heartland instead of existing only
as a formable nation - and since GMA is vanilla, no country file is needed. It
also takes the whole of `slovakia_area`: there is no `nitra_area` in EU4 1.37
and no province called Nitra, but `slovakia_area` is the region meant, holding
five (Hont, Zemplen, Spis, Pozsony, Trencin). Spis and Zemplen are Ruthenian
rather than Slovak, but they are the eastern half of the same Slovak march
lands, so they go over as a block. Opole and Ratibor are all that is left of
`silesia_area` here.

**The Pruthenians.** Vanilla PRU holds nothing at 1444; both Prussian areas are
entirely the Order's, so they pass across whole.

**Crimea.** CRI is the one realm where the question is not "which CK3
character" but "does this polity exist in 867". The tag is vanilla Crimea,
whose ruler in 867 was a Golden Horde appointee - the Crimean Khanate is not
founded until 1441. Its one mod province is Azov, which in 867 is Khazar/Bulgar
steppe, and CK3's nearest real 867 powers are `d_khazaria` and
`k_caspian_steppe`, both held by Manasseh of the Bulanid house. Authoring CRI
needs a decision about what a Crimean realm IS in 867, so it is deferred rather
than given a plausible-looking anachronism (`no_ck3`: no 867 Crimean polity
exists to map; `deferred`: vanilla's file is a 1444 Golden Horde appanage).

**Kept realms whose land this mod never reassigns** are not in `ALL_TAGS`
because the mod does not hand out their land - they keep vanilla's provinces
untouched. They are still realms the mod maintains a court and a size for, so
they still get a deliberate rank. Sardinia is the example: it holds Sassari
(127), Arborea (4735) and Cagliari (2986), all three are in
`NOT_IMPERIAL_867`, so it was never part of the imperial core and releasing it
changes nothing about the 226 provinces the empire decision requires. Spain
also keeps its islands: vanilla takes the Baleares in 1420, so all three stay
with Aragon until claimed. The Order's last three provinces are handed back out
(Neumark, Dramburg, Torun) - not realms of the mod's own: no rank, no capital,
no CK3 title, just the land.

**The Papal State** holds Rome: 118 Roma is deliberately not taken, so PAP still
holds one province on the mod's own account. `country="none"` and no rank
means PAP is tracked here so the CK3 audit can resolve its title - but it is
deliberately NOT a realm the mod maintains: it keeps vanilla's Rome and
vanilla's ruler, so there is nothing to sync a ruler into and no tier to
decide.

## Where the 867 empire was

EMPIRE_CORE_AREAS - the land of the 867 Carolingian Empire, defined as geography
rather than as "whatever five tags happen to hold".

It used to be EMPIRE_KINGDOMS, a list of five tags, which made the empire's extent a
function of the allocation: move a province between realms and the empire silently
changed shape. Worse, it made five tags privileged over the other fifteen, and
Lusatia privileged-in-reverse as the one realm defined by what it was not. This mod
treats every tag on the same terms, so the empire is described by where it was
instead of by who holds it.

These 60 areas are the whole Frankish heartland - the 843 Verdun partition and
everything under it. They contain 237 provinces, of which 11 were never imperial and
are excluded by name below, leaving the same 226 the tag list used to produce. The
areas are the unit because a whole area is usually wholly imperial, and the
exceptions are the interesting part, which is why they are listed rather than
absorbed.

## The eleven non-imperial provinces inside those areas

NOT_IMPERIAL_867 - the 11 provinces inside those areas that the 867 empire did not
hold. Every one is excluded on its own 867 history, never because of who holds it
now, which is the test that keeps this list from quietly re-encoding the tag
privileges it replaced. None of them is excluded for being Lusatian, Breton, Venetian
or anything else; if a province is listed here it is because it was not imperial.

59 Wittenberg, 61 Dresden, 4744 Zwickau - Saxon and Meissen land, east of the
imperial frontier. Thuringia just west of them (Erfurt, Weimar) is inside the
empire, so the line runs through the area rather than around it.
112 Venezia      - an independent maritime republic by 867, never imperial.
118 Roma         - the papal states. The papacy sits outside the emperor's
120 Abbruzzi        succession and holds no imperial land.
127 Sassari, 2986 Cagliari, 4735 Arborea - Sardinia, independent. Corsica, in the
same area, was imperial, which is why 1247 is absent from this list.
2965 Vogtland    - Sorbian-held hinterland of Thuringia, not imperial territory.
This is a judgement about Vogtland in 867, not about Lusatia: Lusatia holds
seven provinces and not one of them is excluded here for that reason.
2988 Tarragona   - Catalonia. The empire held it 801-859 and lost it again before
this date, so 867 has it outside the empire.

## Cultures that do not exist in 867

CULTURE_GONE_867 - vanilla cultures that do not exist yet at this start date,
mapped to what the province should be instead. Applied to every province the mod
writes, keyed on the vanilla culture rather than on a hardcoded province list, so
a province added to the map later cannot be left behind holding a culture that
postdates the scenario.

turkish -> greek, 32 provinces. The Anatolian beyliks - Karaman, Germiyan,
Aydin, Dulkadir, Ramadan and the rest - are a late-13th-century idiom. In 867
this land is Byzantine and Greek-speaking, and the Oghuz Turks have not crossed
into Anatolia at all. Vanilla hands it to a beylik because vanilla starts in
1444, where they are correct.

pontic_greek -> greek, 4 provinces: Kaffa, Trebizond, Canik, Mantrega. This is
not a near miss. The culture is named for the Empire of Trebizond, founded in
1204 by Alexios III and David Komnenos and destroyed by Mehmed II in 1461 - 337
years after this scenario. The Greek population of the Pontic coast was real in
867, since Sinope, Trapezus and Kerasous were Milesian colonies, but a
Trapezuntine in 867 was simply a Byzantine Greek. So greek is right and "Pontic
Greek" is not, rather than the two being neighbours.

There is no `pontic` culture in this game at all. The Pontic *steppe* is a
separate and larger question and is deliberately not touched here: its cultures
are crimean, astrakhani and mishary, none of them Turkish, and the power there in
867 was the Khazar Khaganate. That is its own piece of work.

**Where the rewrite applies.** Culture is rewritten once, at the top-level
province block; religion is rewritten everywhere it appears, because a dated
block that re-sets religion would otherwise leave the province Muslim after
1444.

**The religion carve-outs.** CONQUERED_BY_THE_ARABS - the five of those 32
Turkish-culture provinces that the Abbasids hold, and which therefore keep
Muslim religion: Adana 327, Marash 332, Malatya 2303, Ayntab 4298 and Divrigi
4310. Ayntab and Divrigi really had fallen to the Arabs by 867 (851 and 855);
the other three were still Byzantine and fall in 895-979, so they are this
mod's deliberate early conquest rather than a 867 record. Named explicitly so
the rule reads as "Byzantine land, minus what the Arabs took" instead of
"whatever tag happens to be holding it today".

Two Muslim denominations turn up among the 32, not one: 26 are sunni, and
Malatya 2303, Sivas 329 and Divrigi 4310 are shiite. A rewrite that only
matched `sunni` left Sivas as greek + shiite on Byzantine land, so both are
matched. Malatya and Divrigi are Arab-held and keep theirs either way; Sivas is
the one that silently went wrong.

**No tag-rename pass.** A tag that takes land it did not hold in 867 gets its
own core added by `patch()` the same way every other realm does; the province
keeps the core it already had. Rewriting those tags out of the file - MAM into
EGY, say - would mean the mod's one realm with a special rule was also the one
realm quietly losing history.

### One province whose vanilla comment disagrees

318 Sugla, i.e. Smyrna: vanilla's own comment says "Should not be Greek or
Orthodox in 1444. Its status as a majority Greek city dates to at least after
the 17th Century". That is correct for 1444 - the Aydinids took Smyrna around
1330 and made it Turkish and Muslim - and irrelevant here. This scenario is
867, when Smyrna was Byzantine and Greek, and the Saracen fleet that raided it
did so in 869, two years after the start date, so even that is not yet true at
1444.11.11. The province gets the 867 assignment; this note is where the
argument lives.

## Writing the province files

**The dated-state problem.** EU4 fires every dated history entry up to and
including the start date, in file order, AFTER the undated baseline. Vanilla
therefore overrides the undated owner/controller for any province it hands over
before 1444.11.11 - Verona to Venice in 1405, Aquitaine to England in 1306,
Avignon to the Pope in 1274, East Frisia to EFR, and so on. Patching only the
undated header is not enough, so every allocated province gets a final dated
block (`force_block`) that re-asserts our ownership at the start date and wins.
Appending it last also means we override vanilla, not the other way round, and
`add_core`/`hre` are re-stated there because the same pre-1444 events can drop a
core or re-enable the empire flag.

**The global HRE strip** runs at ANY depth, because the initial flag is not the
only one: dated events such as `1464.1.1` East Frisia and `1548.6.26` Flanders
would otherwise re-join the empire long after 1444.

**Cores.** The mod's core is injected just before the first dated block (the
end of the header) - but only when vanilla does not already grant it: Morea and
Constantinople ship `add_core = BYZ` and are now in the allocation, and without
the skip they would end up with the line twice.

**Unowned land.** An unowned province is a normal EU4 state, not a trick: 1472
vanilla provinces have no owner at all, land included (Grain Coast, Kumasi,
Pensacola), and their files simply carry no `owner` key. A mod province file
replaces the vanilla one for that id, so `unown()` - stripping owner and
controller - just deletes the keys. Cores are deliberately kept: the three
Balaton parking provinces are Hungarian land, and leaving them HUN-cored means
Balaton can inherit them without anyone having to remember which provinces they
were. The province files are the whole truth about the mod: every allocated
province, gifts included, is written - note Venezia is NOT in there, it is
deliberately left vanilla so the base game creates it - and every `hre=yes`
province is written too, because those are the ones that exist only to strip
the flag.

## The empire decision

The decision that forms the empire is defined by **where it was in 867, not by
who holds it**. There is no list of eligible tags in the generator and no realm
that is privileged: the requirement is land, and any tag that comes to hold all
of it may form the empire - including Lusatia, Brittany, and anything added
later, none of which is named as an outsider anywhere because none of them is
one. `empire_core()` comes from build.py, where the 60 areas and the 11
documented non-imperial provinces live, so the decision cannot disagree with
the rest of the mod about where the empire was.

The allow block is `allow: land, and nothing else`. "NOT = { <id> = { ... } }"
is true when that province is not held by you or your non-sovereign subjects,
so requiring every one of them to be false means holding all of them.

The prose the decision shows the player quotes a province count by hand, and it
has already been wrong three times (210, then 221, then 225). The generator
therefore ties all three together - the allocation, the decision, and the
number written for the player - so they cannot disagree again.

## What the land-holder audit enforces

Both checks read build.py's registries rather than keeping a second copy
of the tag list here, because a list in two places is a list that will drift.

* coverage: every tag owning land at the start date must be classified as
either CK3-derived (`TITLES`) or deliberately not (`NOT_CK3`). build.py
derives the set from the generated province files, so a realm added to the
mod later shows up here unclassified instead of escaping the audit. This was
once a private copy of the list that silently went stale twice, letting CRT
and then HUN escape the ownership and empire-frontier checks, so it is
imported rather than re-listed.
* drift: for each CK3-derived tag, name and dynasty must still equal what
CK3 says. Dynasty resolution goes through build.py's own function because
the house-vs-nested-dynasty preference is subtle enough to get wrong twice.

The audit reads `land_holders()` out of the *generated* province files rather
than from a hand-kept list, so it follows the mod instead of an intention: if a
realm gains or loses land, the set changes with it, and it agrees with
`check_start.effective()` by construction - including for provinces whose only
owner is set in a dated block (Azores and Madeira) and for provinces vanilla
leaves unowned.

Coverage runs first, so an unclassified realm is reported even if every mapped
tag happens to agree. A vanilla tag that owns land is NOT unclassified:
nothing here touched it, so it keeps its vanilla ruler, and listing the whole
vanilla roster would only re-type the game data. The gate is for tags the mod
has an opinion about - a realm with no CK3 title has to say why in `Tag.no_ck3`,
or the audit cannot tell "we looked and there is nothing there" from "nobody
has looked". An unexplained gap is a silent one.

A mapped-but-unwritten realm (a CK3 title read, but the mod keeps the vanilla
country file - NAV and PAP are the current examples) is reported as a NOTE, not
a failure: there is no name/dynasty of ours to compare, and the coverage gate
still fails if a land-holder is in neither registry, so this cannot become a
way to skip a realm silently.

## The validator, and the traps it exists for

validate.py runs every check and returns 0 only when the mod is consistent. Its
checks exist because each one caught a real failure once.

**The engine creates only tags it can resolve.** A tag the engine cannot
resolve never exists, so every province naming it as owner resolves to no owner
and renders as uncolonised land - which is what a made-up "LUS" tag did here.
The base game already ships a Lusatia, under the tag SOR, so the mod reuses it;
the check fails loudly if a tag is ever invented again. Vanilla tags are
identified by the "TAG - Name.txt" filenames in `history/countries` -
`common/countries` files carry no tag key at all.

**Ranks are read top-level and as numbers.** Match the TOP-LEVEL key only, and
read the number rather than searching for its text: a substring test passes on
two things that are not a rank at all - a commented-out line, and the same key
indented inside a dated block. Both were live bugs: Bulgaria had
`government_rank = 2` swallowed by the end of a comment on line 4, and France's
only occurrence was inside its 1792 revolution block - so West Francia was a
duchy and the First Bulgarian Empire was too, and the build called both correct.

**Every kept realm, not just the generated ones.** A realm with land and no
`government_rank` of its own silently inherits EU4's default of 1, which is how
realms as large as the Tulunids came to sit level with Silesia - an omission
that reads exactly like a decision in the finished game.

**A realm with land, a name and a rank but no country file is unplayable.** The
gate fails for any such realm that is not an explicitly declared deferral, so a
NEW gap still stops the build; a declared one is reported every time instead of
turning the build permanently red for a reason people learn to ignore. The
realm's seat `effective()` is resolved - including vanilla recipients - and it
must actually hold it, because a tag that owns land but not its own capital is
legal in EU4 yet always a sign of a seat overlooked: Silesia lost Ratibor to
Great Moravia and was left holding three provinces with no seat until its
history was patched.

**A capital that ships differs from a capital that self-declares.**
`Tag.capital` is read by the build only for the realms it generates; for a
hand-written country file it is never consulted, so a wrong number there is
inert rather than wrong - and CRT sat on Diego Suarez Bay in the western Indian
Ocean while its file correctly said 163, with nothing to say so. The check
compares the one declaration against the file that ships and lets a mismatch
fail.

**Age is checked, because the +577 shift** that keeps a king's 867 age also
turns a genuinely young 867 ruler into a child in 1444. A minor monarch must
therefore be flagged `regent = yes`, or the realm is silently ruled by someone
the game thinks cannot rule.

**CK3 is only needed for the name/dynasty cross-check.** Everything else in
validate.py runs without it, so a missing CK3 install skips exactly those
checks with an explicit message instead of taking the whole validator down.

**Double-coring is not itself a defect.** A vanilla core often survives a
historical handover (203 Lyonnais and 204 Dauphine are FRA-cored in vanilla but
Lotharingian in 867), so only double-coring that is not backed by ownership is
flagged. Vanilla cores are compared as the plain strings they are: no realm is
a rename of another, so a province the mod hands to a new owner keeps the core
it already had and simply gains one more - anything else would be a rename
pass, and those tend to hide real core loss behind a mapping. A tag survives if
it still holds a vanilla INITIAL core outside the five kingdoms; tags whose
entire land sits inside a kingdom cannot be released, which is an accepted
consequence of reassigning European provinces, not a defect. Only the
reassigned provinces matter on the ownership side - the other overridden files
exist solely to strip `hre=yes` and legitimately keep their vanilla owner.

**Registries are bigger than holders.** `TITLES` + `NOT_CK3` describe 31
tags; the land-holders at the start date number 29 - two CK3-mapped realms hold
no land at all. Adding the registries together once claimed to explain 29
holders with 31 tags, which is how a partition check stops being one, so the
audit intersects the actual holders instead. The remaining union of "excused as
vanilla and untouched" is reported, not asserted - the union is a tautology -
but it is only true of a realm this mod leaves alone: one it gives a rank to is
not untouched just because its provinces stayed vanilla, and BOH and SAR both
hold land this build never allocated. Anything managed has to be classified on
purpose.

**Derived registries stay derived.** `RULER_TAGS` (realms the mod gives an 867
ruler to that are not Tags themselves - written files and vanilla copies) is
derived from the Tags, which keeps the two sets disjoint by construction; as a
hand-kept list it overlapped (GMA and SIL were checked twice) and drifted. The
ruler-drift check iterates `build.TITLES`, the one registry, so a realm added
there is checked with no second list to update - an earlier copy of that list
sat in validate unused and still claimed CK3 models no Crete. It does, as
`d_krete`.

**BOMs are mandatory.** Every localisation file must start with a UTF-8 BOM:
all 143 vanilla `*_l_english.yml` files do, and the engine silently discards
any that do not - no error, no log line, the file just never loads. That is
exactly how the realm names stayed "France" and "Germany" while this mod's file
looked correct. The scan is walked recursively, because `localisation/replace/`
is where overrides of vanilla keys must live and a flat scan skipped it
entirely - the one folder whose files matter most here.

**An empty country file looks clean.** "No `elector = yes`" reads the same to
every grep whether a file is complete or 0 bytes, and a crashed generator can
produce exactly that. A size check catches it.

**Culture and religion follow the generator's table**, not a hardcoded list of
37 province ids, so a province added to the map later is caught instead of
quietly staying Turkish. Culture alone is not enough: Sivas 329 is vanilla
shiite, not sunni, so a sunni-only rewrite left it greek + Muslim on Byzantine
land without failing anything - hence the religion assertion too. Vanilla is
not consistent about file-name separators ("318 - Sugla" but "1853- Kastoria"),
so the digits are read off the front of the name rather than splitting on
" - ".

## The Tag database

A `Tag` is a realm this mod is *responsible for*: one it keeps a country file,
a rank and a court for. That is not the same as a tag that appears in the
allocation. Vanilla leftovers this mod deliberately does not touch - Brittany,
Venice, the other electors - are not Tags and are not tracked here. They hold
land and that is fine; the mod has no opinion about them.

Two axes are easy to confuse:

```
managed   this mod keeps a realm for it: country file, rank, court, audit
in_alloc  the allocation may hand it a province
```

VEN is in_alloc but not managed - it keeps its namesake province and survives
as a maritime republic with vanilla's ruler. BOH and PAP are managed but not
in_alloc: BOH's land is never reassigned, it just keeps a court; PAP keeps
vanilla's file entirely (see above). Both are ordinary, and conflating them is
how Lusatia ended up defined by what it was not.

Everything the generators need is an attribute of the realm: what it is called,
how big it is, where its land is, which CK3 title its ruler comes from, and
why. Adding a realm means adding one object to `TAGS`, not editing six tables
in four scripts. The same fact used to be spelled out separately in
modtags.py, gen_provinces.py, gen_countries.py, ck3ruler.py and validate.py -
five copies is four ways to be wrong, and the copies had already drifted:
gen_countries.py still treated Lusatia as a partition kingdom while the mod's
own localisation had always described a five-kingdom empire with Lusatia
outside it, and a realm that appeared in the allocation but not in ck3ruler's
TITLES or NOT_CK3 was unclassifiable without anyone noticing.

Nothing about land lives outside this file. `AREA_OWNERS` and `PROVINCE_OWNERS`
are derived from `Tag.areas` and `Tag.provinces`, and build.py derives its
allocation from the same two lists - there is no second copy to drift.
Per-realm data notes on the fields:

- `rank` - EU4 `government_rank`: 1 duchy/principality, 2 kingdom, 3 empire.
  Every rank is argued from the realm's own 867 standing, never from which
  group a tag was filed under. An unargued tier is how the Tulunids ended up
  ranked level with Silesia. `rank` is None only for a deferred realm, and only
  for PAP, which is not managed at all.
- `capital` - province id, or None to keep vanilla's own seat.
- `culture` - primary culture for a from-scratch country file.
- `ck3_title` - the CK3 title whose 867 holder supplies the ruler's name and
  dynasty. None means CK3 is not the authority - see `no_ck3`.
- `no_ck3` - why CK3 is not the authority, when `ck3_title` is None. Required
  if `ck3_title` is None and the realm is not deferred: an unexplained gap is
  a silent one.
- `deferred` - why no country file is written yet, or None. A deferral, not an
  exemption.
- `areas` / `provinces` - the whole declaration of a realm's land: EU4 areas
  taken whole (layer 1), then individual provinces carved out (layer 2). There
  is no third list and no block table. The overrides exist because EU4 areas
  straddle 867 borders - an area is a modern administrative unit, not a
  Carolingian one - so the province inside it that belongs elsewhere has to be
  pulled back out by hand, and the reasoning next to each override was always
  per-realm.
- `provinces` is a frozenset, not a list: once the layers are applied the order
  carries no meaning, and a province appearing twice was only ever a sign that
  two blocks had overlapped - 12 did, and 12 are now gone rather than
  deduplicated away. Callers may write either a tuple or a set literal; the
  field is a set either way.
- `country` - what build.py does with this realm's country file, and the whole
  instruction (see the modes table above).
- `elector` - True when this realm is an elector of the HRE, so its 1444 vote
  goes. ALL_TAGS additionally states the derived set: the tags the allocation
  may hand a province to, which is not the same set as the managed realms.
- `holder_heir_dynasty` - True when this realm's heir starts a new house, so
  `--fix` must not overwrite the heir's dynasty from CK3. No realm sets it yet,
  but the field is why the sync rewrites the whole 1444.1.1 block.
- `rank_note` - used to argue every rank in place. The argument now lives in
  this document (below).

### Ranks, argued

Each realm's rank is a decision about that realm in 867, not a formula. The
arguments, as written on the Tags:

- **FRA - kingdom.** West Francia is the largest of the partitions. Charles the
  Bald was King of the Franks from 843 and held nothing higher in 867 - the
  imperial crown came in February 875, when Pope John VIII crowned him in Rome,
  eight years after the start date. (FRA is vanilla's rank 3; the mod patches
  it to 2.)
- **LOT - kingdom.** Lotharingia: a kingdom, though a hollow and contested one.
- **GER - kingdom.** East Francia: a kingdom ruled in its own right.
- **BAV - duchy, and deliberately not rank 2.** Bavaria is a DUCHY in 867, not
  a kingdom, and that is true whether or not it is independent. Carloman
  governs it from c. 863 but is not crowned king until 876, so a rank-2
  Bavaria would assert a crown nine years early.
- **ITA - kingdom.** Louis II was king of Italy as well as emperor, so Italy is
  a kingdom held under an imperial claim, not the empire itself.
- **LUS - duchy.** A Sorbian duchy, small in 867 on any measure.
- **NAV - kingdom.** The Kingdom of Pamplona under Garcia I, a kingdom in 867
  and a peer of the Asturians.
- **AST - kingdom.** Alfonso III inherited the kingship in 866, one year before
  the start date, so it is a kingdom and not a county.
- **ADU - kingdom.** Al Andalus is the Umayyad emirate, seated at Cordoba (225)
  and supplied its 867 ruler by CK3's `k_andalusia`. It holds all of
  al-Andalus plus Aragon, Madrid, the Canaries, Madeira and Ceuta, and a
  smaller tier would undersell it.
- **CRT - duchy.** An Emirate of Crete is a single-island emirate under Abu
  Hafs Umar; a duchy is the closest tier EU4 offers. CK3's `d_krete` is already
  held in 867, by Shuayb - Abu Hafs' father, who lost the island to his own son
  in 870.
- **ARB - empire.** The Abbasid Caliphate, which in 867 is the empire of the
  Islamic world and no realm in this table rivals it.
- **TUL - kingdom, contested.** The Tulunids held Egypt and Syria as a de facto
  independent beylikh, but a beylikh is a principality, and EU4's only tiers
  are duchy and kingdom. Kept at 2 so the Tulunids are not ranked level with
  Silesia on the strength of a naming gap.
- **SIL - duchy.** A Piast duchy, small but not a titular one.
- **GMA - kingdom.** Great Moravia under Rastislav, a kingdom in its own right.
- **DAL - duchy.** A coastal duchy of city-states, nominally one realm.
- **BYZ - empire.** The Empire itself. 867 is Basil I's first full year.
- **BUL - kingdom.** The First Bulgarian Empire under Boris, a kingdom by 867
  and a peer of Byzantium's neighbours rather than a vassal duchy.
- **HUN - duchy, contested.** The Principality of Hungary under the Arpad was a
  principality, not a kingdom, until 1000 - so 1 is the literal answer, yet the
  realm is a major power in 867 and EU4 has no tier between a duchy and a
  kingdom to say so. Kept at 1 on the strength of the literal fact rather than
  the mod's ambitions for it.
- **MON - duchy.** Duklja under Miroslav, a coastal Serbian principality.
- **PRU - duchy.** Prussia from CK3's `d_prussia`: the Pruthenians, whom EU4
  can only seat in a Catholic duchy.
- **CRI - duchy, contested.** There is no Crimean polity in 867 at all. Rank 1
  is provisionally in place so the tag is playable while its identity is
  settled.
- **BOH - duchy.** Bohemia is a duchy of the Empire under Borivoj I. Rank 1 is
  the literal 867 answer and is NOT demotion for standing outside the
  partition: Bohemia is a small march here for the ordinary reason, that in 867
  it was a small duchy.
- **SAR - duchy.** Sardinia, holding Sassari (127), Arborea (4735) and Cagliari
  (2986), all three in `NOT_IMPERIAL_867`, so neither the empire nor the
  release changes. A duchy is the honest tier for one independent island.

### Derived views

Every one of these is a projection of `TAGS`, never a second copy:

- `AREA_OWNERS`, `PROVINCE_OWNERS` - layers 1 and 2, and therefore the whole
  allocation standing. Layer 2 is inverted back to the province -> tag shape
  the allocator wants; per-realm on the Tag because the reasoning is per-realm.
- `ALL_TAGS` - the tags the allocation may hand a province to. Not the same set
  as the managed realms: BOH and SAR are maintained but their land is never
  reassigned.
- `BY_TAG` - the one lookup map, by tag string.
- `ELECTORS` - the seven electors of the HRE. Every realm here is stripped of
  its 1444 vote, which is the whole of the mod's diplomacy with a dissolved
  empire.
- `RANK` - `government_rank` per realm; `KEPT_REALMS`, `DEFERRED_REALMS` - kept
  but not yet authored, each with the reason, reported on every build.
- `TITLES`, `RULER_TITLES`, `NOT_CK3` - CK3 title per realm; the few realms
  whose ruler is read from a CK3 title other than their own; and realms that
  own land but whose ruler is not CK3's to supply, with the reason. NOT_CK3
  holds only realms this mod decides something about: a vanilla tag that owns
  land is not in there because listing the whole vanilla roster would just be
  game data retyped.
- `EMPIRE_KINGDOMS` - the five kingdoms of the empire, in the order the mod
  presents them: West Francia, Lotharingia, East Francia, Bavaria, Italy.
  Lusatia is deliberately not here - it is a principality outside the empire,
  not a sixth kingdom. Stated rather than derived, because no single field
  picks these five out: rank gives four of them and misses Bavaria (a duchy);
  country gives them plus Lusatia. Any rule that produced the set would be a
  rule that could also produce a different one, which is what a named list
  avoids. It was once a private literal in validate.py, where nothing connected
  it to the order the realms are declared in; selfcheck pins the two together.
- `BALATON_RESERVED` - Balaton, Krain and the Danube bend. Hungary keeps the
  basin, and these three are carved out of it rather than added to it.
- `ALL_TAGS`/`BY_TAG` naming - a hand-kept copy of the recipient set is a
  duplicate waiting to drift, exactly the class of bug the deleted
  `cache/alloc.json` was.

`selfcheck()` fails loudly on a database that contradicts itself - a tag that
declares land with `in_alloc` off, a realm with a rank and no argument, a
`deferred` realm that also writes a file, the `EMPIRE_KINGDOMS` order drifting
from the declaration order - before any generation runs.
